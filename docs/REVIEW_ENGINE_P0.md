# Review Engine P0

P0 separates the review entrance from inference. It does not combine Native and
Attribution approval (P1), or change Operator admission (P2).

## Boundaries

| Layer | Responsibility | Authority |
| --- | --- | --- |
| `read_model` | Existing bounded Context, Item Context, Evidence and exact Canonical resolution | Read only |
| `review_engine.ReviewEngine` | Configured reviewer binding, policy, native Advice validation and immutable publication | MODEL Advice only |
| `review_execution` | Whole-packet input/output contract, structured reasoning, inference checkpoints and replay | Calls the same Engine submission |
| `review_backends` | Existing `ChatLLM` transport to an OpenAI-compatible API or loopback Ollama | Inference only |
| MCP `WriteService` | Existing 19-tool contracts, delegates Advice to Engine | Existing scoped Advice/Proposal permissions |
| Workbench / Operator | Human decisions, Native and Attribution seals, independent admission | Unchanged |

Previously the shared read contracts lived inside `pro_a.mcp`, and reviewer
execution binding lived in `mcp.write_service`. The read implementation now lives
in `read_model`; the old modules are import aliases, including private helpers,
to retain existing imports and MCP schemas. Native semantic validators remain
in `workbench.advisory_review`, `review_policy` and Evidence Binding v2.
The core imports neither `mcp` nor `pro_a.mcp`. Distribution dependencies remain
unchanged so ordinary installations retain their existing MCP command.

`MCP_ADVICE_CONTEXT` remains the historical event name for configured execution
provenance across all channels. Its schema and Human batch checks are unchanged.
The name does not imply platform attestation. Configured model identity and
provider response metadata are distinct; neither establishes platform identity.

## Three paths

1. ChatGPT reads the existing MCP Context/Item Context, then submits the existing
   Advice payload through `submit_reviewer_advice` → `ReviewEngine.submit`.
2. A trusted program calls `ReviewEngine.run` with `CompatibleBackend` → shared
   input, inference, normalized output, then `ReviewEngine.submit`.
3. The same program supplies `OllamaBackend` → the same run and submission path.

The API here is a Python API, not a new public HTTP endpoint. No new production
configuration is automatically enabled. Creating an enabled `ReviewerConfig`
is a trusted operator action, never a model-supplied field. Artifact allowlisting
and a valid pre-existing Human-selected policy are required. Historical packets
without a policy retain the existing dual-review interpretation. Dual mode still
requires operator-attested isolation and independent execution identities;
changing the transport or retrying inference cannot create a second reviewer.

Example for an already qualified, isolated Workbench configuration:

```python
from pro_a.config import LLMConfig
from pro_a.review_engine import ReviewEngine, ReviewerConfig
from pro_a.review_backends import CompatibleBackend, OllamaBackend

# config is an existing validated WorkbenchConfig; these identities are supplied
# by the operator, not generated by inference. Do not use a frozen historical SHA.
engine = ReviewEngine(config, ReviewerConfig(
    enabled=True, artifact_ids=(artifact_id,), slot="A",
    reviewer_id=reviewer_id, execution_id=execution_id, model=model,
    review_mode="SINGLE_MODEL_HUMAN", isolation_attested_by_operator=False,
))
remote = CompatibleBackend(LLMConfig(
    enabled=True, base_url=qualified_url, api_key_env="REVIEW_API_KEY", model=model,
))
local = OllamaBackend(model)  # existing loopback service; does not start/download one
# Choose ONE qualified backend. A run can persist MODEL Advice, not a proposal.
result = engine.run(artifact_id, current_blind_context_sha, remote,
                    task_id="operator-assigned-task-id")
```

Remote credentials use the existing environment-variable mechanism. The local
adapter accepts only loopback URLs without user info, query or fragment. It uses
Ollama's OpenAI-compatible endpoint, with no provider-specific `thinking` field.
Both reuse existing timeouts and sanitized attempt diagnostics, with automatic
network retries disabled. The adapter does not inspect or start local models.

## Contract and failure handling

Input includes the current blind Context and full Candidate contents/Evidence,
content identities, bounded Canonical resolution, formal Policy and fixed reviewer
configuration. Existing limits apply; oversized or unavailable context fails
before inference rather than being silently truncated.

Output must contain the exact Context SHA and every Candidate exactly once, with
the exact Content SHA, `SUPPORTED / UNSUPPORTED / UNCERTAIN`, and nonempty reasoning
fields `summary`, `evidence`, `subject`, `time`, `numbers`, `qualifiers`, and
`canonical_resolution`. Unknown fields, including claimed Human identity, fail.
Structured reasoning is encoded as canonical JSON in the existing Advice reason
string; MCP's historical free-text reason remains compatible. Both end at the
same native validators. Context and policy are re-read after inference and again
by native submission. No output upgrades source assertions to verified facts or
changes Current View Use.

Private execution records live under the configured artifact root in
`review-executions/<artifact-and-task-hash>/`. They are not Canonical data or
Operator grants. Request identity binds input, reviewer, backend configuration
and prompt. Records must be retained with private Workbench artifacts, never
published with source code.

- Invalid output or request failure: immutable `FAILED` result with a fixed code
  and sanitized attempt metadata; no Advice. Repeating the task returns its result.
- Deliberate retry after a known failure: use a new task ID with the same reviewer;
  it is another attempt, not an independent review.
- Successful response: immutable response checkpoint before Advice publication.
  Repeating the same task resumes this response without another model call.
  Native Advice publication remains content-idempotent.
- Process interruption after inference started but before a durable response, or
  a remaining exclusive execution lock: `REVIEW_EXECUTION_RECOVERY_REQUIRED`.
  There is no automatic retry or lock deletion. Inspect the owning process and
  private request/response/Advice registration before any manual recovery.
- Changed input, model, execution identity or backend configuration cannot reuse
  the task. A stale Context or sealed Packet fails; no state is reset.

The journal adds no database schema or governance states. A crash after native
Advice publication can be recovered by exact replay, retaining native file and
registration checks. Human-approved state is never undone by retry.

## Qualification limits

Synthetic tests exercise all three entrances on the same Packet, real loopback
HTTP transport for both inference adapters, failures/replay, existing Human gates,
historical reads and Runtime Guard. Mock transport is not a real Provider call.
Without a qualified live local model, technical and output-contract qualification
do not establish semantic review quality. Real inference and production review
remain separate qualified operations. No historical Apply is replayed for P0.
